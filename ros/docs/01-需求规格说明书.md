## 1. 引言

### 1.1 编写目的

本文档定义「ROS 2 仿真巡逻机器人系统」的**范围、功能需求、非功能需求与验收标准**，
作为后续架构设计、详细设计、测试与验收的唯一需求依据。

### 1.2 项目背景

在机器人/具身智能方向的技术岗应聘中，普遍存在的问题是：
学历与汽车电子/嵌入式背景尚可，但缺少一个**能跑、能演示、能讲清架构**的机器人项目。

市面上常见的"三天速成项目"存在两类失败模式：

| 失败模式 | 表现 | 后果 |
| --- | --- | --- |
| 好高骛远 | 选机械臂 MoveIt2 抓取、真机调试、强化学习训练 | 三天跑不通，交付物为零 |
| 过度简单 | 只跑一个 `ros2 run demo_nodes_cpp talker` | 无系统集成含量，面试无话可讲 |

**本项目的策略**：不追求算法创新，而是选择**生态成熟、文档齐全、可稳定复现**的开源栈
（TurtleBot3 + Gazebo + SLAM + Nav2），在其之上用 **C++ 自研任务层**（巡逻状态机 + 安全守护），
用"系统集成 + 工程化"作为能力证明点。

### 1.3 需求来源

| 来源 | 提炼出的需求 |
| --- | --- |
| 岗位画像：机器人 TPM / 系统工程师 | 多模块联调、接口定义、参数化、可观测性、进度可控 |
| 岗位画像：ROS 开发 | 用 C++ 而非 Python、使用 Action/参数/生命周期等 ROS 2 原生机制 |
| 交付约束：3 个工作日 | 必须依赖成熟开源栈，禁止自研底层算法 |
| 个人背景：汽车电子系统集成 | 突出「传感器 → 通信 → 决策 → 执行」的链路一致性 |

## 2. 项目范围

### 2.1 纳入范围（In Scope）

1. 基于 Gazebo 的移动机器人仿真世界与 TurtleBot3 Burger 模型加载。
2. 激光雷达（LiDAR）与里程计传感器的数据链路打通。
3. 使用 SLAM 工具离线构建栅格地图并持久化。
4. 基于已保存地图的 AMCL 定位与 Nav2 自主导航。
5. **C++ 自研**航点循环巡逻任务节点（含状态机、重试、超时、可视化）。
6. **C++ 自研**激光安全守护节点（前向扇区障碍检测 + 迟滞逻辑 + 紧急暂停）。
7. 自定义 ROS 2 接口（1 个 msg、1 个 srv）。
8. 全链路参数化（YAML）与一键 launch 启动。
9. 全套开发文档、演示脚本、架构图与录屏资产。

### 2.2 不纳入范围（Out of Scope）

| 排除项 | 排除理由 |
| --- | --- |
| 自研 SLAM 算法 | 数学门槛高，三天不可能完成；工程上也不应重复造轮子 |
| 自研全局/局部规划器 | Nav2 已提供成熟实现（NavFn/Smac、DWB/MPPI） |
| 强化学习 / 端到端控制 | 训练不稳定、不可复现、无法在此周期内收敛 |
| 真实硬件部署 | 硬件调试不可控，无法保证三天交付 |
| MoveIt2 机械臂抓取 | 配置复杂度高（URDF/SRDF/规划组），三天风险过高 |
| 多机器人协同 | 需引入命名空间、多机 DDS 配置，超出范围 |
| 自定义 URDF 机器人模型 | 列入 v0.2 迭代（见 14 文档 Roadmap） |
| 视觉感知（YOLO 目标检测） | 列入 v0.3 迭代，本期仅预留扩展点 |

## 4. 术语与缩写

见 [`15-术语表与参考资料.md`](15-术语表与参考资料.md)。本文档使用的关键概念：

- **航点（Waypoint）**：地图坐标系下的一个目标位姿 `(x, y, yaw)` 及可选的停留时间。
- **巡逻（Patrol）**：按顺序循环访问一组航点的任务。
- **栅格地图（Occupancy Grid Map）**：SLAM 输出、Nav2 使用的二维占据栅格地图。
- **安全守护（Safety Guard）**：独立的轻量节点，监控激光雷达数据，在障碍过近时请求任务层暂停。

## 5. 功能需求（FR）

> 优先级说明：**P0** = 必须交付（决定演示能否进行）；**P1** = 应该交付（加分项）；**P2** = 可选（时间允许再做）。

### FR-01 仿真环境一键启动 `P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 提供单个 launch 文件，启动 Gazebo 世界、加载 TurtleBot3 Burger、发布机器人状态与 TF |
| 输入 | 无（可选参数：世界文件名、机器人型号） |
| 输出 | Gazebo 窗口显示带障碍物的世界；`/scan`、`/odom`、`/tf` 正常发布 |
| 约束 | 启动后 60 秒内所有话题就绪 |
| 验收 | `ros2 topic hz /scan` 稳定输出（仿真中约 5–10 Hz） |

### FR-02 键盘遥控 `P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 支持通过键盘发布 `/cmd_vel` 控制机器人移动，用于建图和应急干预 |
| 输入 | 键盘按键（i/j/k/l/空格等） |
| 验收 | 按键后 Gazebo 中机器人产生对应运动 |

### FR-03 SLAM 建图与地图持久化 `P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 启动 SLAM 节点在线建图，RViz 显示地图；支持将地图保存为 `.pgm` + `.yaml` |
| 输入 | `/scan` + `/odom` + `/tf` |
| 输出 | `maps/tb3_world.pgm`、`maps/tb3_world.yaml` |
| 验收 | 保存的地图能重新加载并在 RViz 正确显示，与实际世界障碍布局一致 |

### FR-04 定位（AMCL）`P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 加载已保存地图后，使用 AMCL 进行蒙特卡洛定位，支持 RViz 的 `2D Pose Estimate` 设置初始位姿 |
| 输出 | `map → odom` 变换；`/amcl_pose` 话题 |
| 验收 | 机器人运动后 `/amcl_pose` 收敛，RViz 中位姿与 Gazebo 中实际位置偏差小于 0.3 m |

### FR-05 单点导航 `P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 支持通过 RViz 的 `Nav2 Goal` 工具下发单点导航目标，机器人自动规划路径并到达 |
| 接口 | Nav2 `navigate_to_pose` Action |
| 验收 | 在无障碍场景下，5 个不同目标点成功率达到 5/5 |

### FR-06 航点循环巡逻（核心自研）`P0`

| 项 | 内容 |
| --- | --- |
| 描述 | C++ 节点按顺序循环访问配置的航点，到达每个航点后等待指定时间，再前往下一个；走完全部航点后按 `loop` 参数决定是否重新开始 |
| 输入 | 航点列表（参数化）；Nav2 `navigate_to_pose` Action 服务可用 |
| 输出 | 机器人自主移动；巡逻状态话题；可视化 Marker |
| 子需求 | FR-06.1 支持配置 ≥ 3 个航点<br>FR-06.2 支持每个航点独立停留时间<br>FR-06.3 支持航点总数与 `x/y/yaw/wait` 数组长度不一致时报错并拒绝启动<br>FR-06.4 支持实时反馈剩余距离（透传 Nav2 feedback）<br>FR-06.5 巡逻循环次数可配置（0 = 无限循环） |
| 验收 | 3 个航点、循环 2 轮，全程无人工干预，成功率 100%；日志中每个航点的开始/到达/离开均有记录 |

### FR-07 巡逻模式控制服务 `P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 提供自定义服务 `patrol_interfaces/srv/SetPatrolMode`，支持 5 种模式：`START` / `PAUSE` / `RESUME` / `STOP` / `RESET` |
| 语义 | `START` 从当前航点索引开始巡逻；`PAUSE` 取消当前导航目标并保留索引；`RESUME` 从保留索引继续；`STOP` 取消并归零索引回到 IDLE；`RESET` 重置失败计数与统计信息 |
| 输出 | 服务响应含 `success: bool` 与 `message: string`（失败时给出原因，如 `ALREADY_RUNNING`、`NAV_SERVER_UNAVAILABLE`） |
| 验收 | 5 种模式各执行一次，状态迁移与 04 文档的状态迁移表完全一致 |

### FR-08 巡逻状态发布 `P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 以 ≥ 1 Hz 频率发布 `patrol_interfaces/msg/PatrolStatus`，包含：运行模式、当前航点索引、当前航点总数、已完成航点数、当前循环次数、到目标剩余距离、最近一次错误码与错误信息 |
| 约束 | 话题采用 volatile 可靠性，保证 1 Hz 持续发布（便于 `ros2 topic echo` 观察） |
| 验收 | `ros2 topic echo /patrol/status` 输出字段随巡逻进度变化 |

### FR-09 航点可视化 `P1`

| 项 | 内容 |
| --- | --- |
| 描述 | 发布 `visualization_msgs/MarkerArray`，在 RViz 中显示航点：灰色 = 未访问，黄色 = 当前目标，绿色 = 已完成 |
| 输出 | `/patrol/markers` |
| 约束 | Marker `frame_id = map`，`lifetime = 0`（持续显示），`ns` 区分不同航点避免 ID 冲突 |
| 验收 | RViz 中 Marker 颜色随巡逻进度实时变化 |

### FR-10 激光安全守护（核心自研）`P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 独立 C++ 节点订阅 `/scan`，在前向扇区（默认 ±30°）内计算最小障碍距离；当距离小于 `stop_distance` 时置位紧急标志，大于 `resume_distance` 时复位（迟滞，避免抖动） |
| 输出 | `/safety/nearest_obstacle_distance`（`std_msgs/Float32`）、`/safety/emergency_stop`（`std_msgs/Bool`，transient_local 便于后启动节点获取当前状态） |
| 联动 | 巡逻节点订阅紧急标志，置位时调用 Nav2 的 cancel 接口暂停当前导航；复位后从当前航点重新发起导航 |
| 子需求 | FR-10.1 无效数据（`inf`/`nan`/空数组）必须过滤，不得误触发<br>FR-10.2 迟滞区间必须满足 `resume_distance > stop_distance`，否则参数校验失败<br>FR-10.3 默认**不直接发布 `/cmd_vel`**，避免与 Nav2 控制器冲突（通过参数 `allow_cmd_vel_override` 显式开启，默认 `false`） |
| 验收 | 在机器人前方 0.3 m 处放置障碍物，`/safety/emergency_stop` 变为 `true`，机器人停止前进；移开障碍物后自动恢复 |

### FR-11 失败重试与超时保护 `P1`

| 项 | 内容 |
| --- | --- |
| 描述 | 单个航点导航失败（Action 返回 ABORTED）时自动重试，最多 `max_retries` 次；单航点导航超过 `waypoint_timeout` 秒则主动 cancel 并计入失败 |
| 策略 | 超过重试上限后，`skip_failed_waypoint=true` 则跳过该点继续下一个；否则整个任务进入 `FAILED` 状态 |
| 输出 | 状态消息中体现失败次数与错误码；日志 WARN 级别记录 |
| 验收 | 人为把一个航点设在墙体内部，观察重试与跳过行为符合配置 |

### FR-12 参数化与一键启动 `P0`

| 项 | 内容 |
| --- | --- |
| 描述 | 所有可调量（航点、速度限制、超时、阈值、话题名、坐标系）通过 YAML 参数暴露；提供 4 个 launch：`simulation` / `mapping` / `navigation` / `patrol` |
| 约束 | 参数声明必须带默认值；话题名与坐标系名支持参数覆盖 |
| 验收 | 仅修改 YAML 即可改变航点数量与巡逻行为，无需重新编译 |

### FR-13 运行时日志与诊断 `P1`

| 项 | 内容 |
| --- | --- |
| 描述 | 状态迁移、航点切换、导航失败、安全触发均输出结构化日志（含节点名、状态、航点索引、数值） |
| 约束 | 日志级别可运行时调整（`ros2 param set /patrol_node log_level debug`）；高频反馈不打 INFO 日志避免刷屏 |
| 验收 | 一次完整巡逻的日志可独立还原出执行时间线 |

### FR-14 自定义 ROS 2 接口 `P0`

| 项 | 内容 |

## 8. 验收标准（Definition of Done）

- [ ] 代码已合入仓库，通过 `colcon build` 与 `colcon test`
- [ ] 对应的功能需求在仿真环境实测通过，且有日志或录屏为证
- [ ] 相关文档（04/05/09）已同步更新
- [ ] 关键参数已在 YAML 中暴露，无硬编码魔法数字
- [ ] 无未处理的 TODO 阻塞主流程

## 10. 需求变更流程

1. 提出变更（记录在 14 文档的变更记录中，含理由与影响面）。
2. 评估对 FR / 排期 / 验收项的影响。
3. 若影响 P0 需求或验收线，必须在**当天**决定：接受、降级为 P1/P2、或移入 Roadmap。
4. 更新本文档版本号与 RTM，再同步到架构与详细设计文档。

> **冻结原则**：设计冻结（v0.1 发布）后，P0 需求不再变更；新增需求只能进 Roadmap。
