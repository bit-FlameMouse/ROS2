## 1. 演示目标

**一句话目标**：让看的人相信——「这个人能独立把一个多模块机器人系统搭起来、跑通、讲清楚。」

| 要传达的信息 | 靠什么体现 |
| --- | --- |
| 系统整体能力 | 一条命令启动全链路 |
| 工程深度 | 自研 C++ 状态机 + 安全守护（不是调包） |
| 架构清晰 | 分层图 + 模块边界 |
| 对细节的掌控 | TF、QoS、生命周期、超时重试这些"细节"都能讲 |
| 结果导向 | 机器人在跑，不是 PPT |

**不要传达的信息**：❌ "我用 AI 写的"、❌ "就是跑了个开源 demo"、❌ "算法是我自研的"（这是假的）。

## 4. 3 分钟演示分镜脚本

> 时间为累计时间。每个镜头都给了「操作」与「讲解词」，讲解词可直接照念。

### 镜头 1｜开场：项目定位（0:00–0:20）

**操作**：停留在 README 或架构图页面（或干脆对着 Gazebo 与 RViz 说）。

**讲解词**：

> "这是我做的一个 ROS 2 移动机器人仿真系统。它基于 ROS 2 Humble 和 Gazebo，
> 用 TurtleBot3 做平台，实现了**从建图、定位、导航到自主巡逻**的完整链路。
> 主开发语言是 C++，规模不大，但分层和接口是完整的——下面我用三分钟把它跑一遍。"

**要点**：先说清楚"是什么"，不要一上来就讲技术细节。

---

### 镜头 2｜架构一页图（0:20–0:50）

**操作**：切到 `docs/02-系统架构设计说明书.md` 的分层图（或提前打开图片）。

**讲解词**：

> "整体分成五层。最下面是 Gazebo 仿真层；上面是 ROS 2 的通信抽象层；
> 再上面是导航与建图层，这一层我用的是成熟开源栈——SLAM Toolbox 建图、AMCL 定位、Nav2 做规划和控制。
> 第四层**任务层是我自己写的**，两个 C++ 节点：`patrol_node` 负责巡逻任务编排，
> `safety_guard_node` 负责激光安全监控。最上面是交互层，RViz 加命令行。
>
> 这里有个刻意的设计：**自研部分只依赖 Nav2 的 Action 接口**。
> 也就是说，如果把 Gazebo 换成真车，任务层代码基本不用改。"

**要点**：快速过，重点是"我在哪一层做了什么、为什么这么分"。

---

### 镜头 3｜一条命令启动（0:50–1:10）

**操作**：在终端 A 执行：

```bash
ros2 launch patrol_robot_bringup patrol.launch.py
```

等待 Gazebo 与 RViz 起来（约 10 秒），可同时执行 R-01 检查。

**讲解词**：

> "一条命令启动全部：仿真世界、机器人、Nav2 的完整导航栈，还有我的两个任务节点。
> 注意任务层是**延迟 8 秒启动**的——因为 Nav2 的生命周期管理器要按顺序激活
> map_server、AMCL、planner、controller、bt_navigator，
> 太早发目标会被静默丢弃。这是个很典型的坑。"

**要点**：这句话直接展示了"你踩过坑"，比说"我用了 Nav2"有说服力。

---

### 镜头 4｜地图与定位（1:10–1:35）

**操作**：

1. 在 RViz 中点 `2D Pose Estimate` 设置初始位姿。
2. 指出 RViz 中 `/scan` 点云与地图墙体对齐。

**讲解词**：

> "地图是我用 SLAM Toolbox 采集的——遥控机器人走一圈，把栅格地图存下来。
> 现在是导航模式，AMCL 在这个地图上做蒙特卡洛定位。
> 你看红色的激光点云和地图的墙线是对齐的，说明定位收敛了。
> 这一步是后续所有导航的前提——地图不对，后面全都不对。"

**要点**：强调"地图与定位是地基"。

---

### 镜头 5｜航点可视化（1:35–1:50）

**操作**：在 RViz 中放大 `/patrol/markers`，指出灰色/黄色圆点与 `WP0`、`WP1` 标签。

**讲解词**：

> "这些是我发布的航点标记，用 MarkerArray。
> **灰色是还没去的点，黄色是当前目标，绿色是已经走完的点**。
> 颜色由状态机驱动，实时更新——所以看一眼 RViz 就知道任务走到哪了。"

---

### 镜头 6｜启动巡逻 + 状态流（1:50–2:25）

**操作**：

1. 终端 C 执行：

```bash
ros2 service call /patrol/set_mode patrol_interfaces/srv/SetPatrolMode "{mode: 0}"
```

2. 切到终端 B，展示 `/patrol/status` 的实时输出：`mode`、`current_waypoint_index`、`distance_remaining`。

3. 让机器人走完第 1 个航点，指出 Marker 由黄变绿。

**讲解词**：

> "调用我自定义的服务让机器人开始巡逻。返回 success，当前模式变成 1，也就是 MOVING。
>
> 右边的状态话题是我定义的消息，一赫兹发布：当前模式、当前目标航点索引、
> 已完成航点数、剩余距离、错误码。
>
> 你看它到达第一个点后，模式从 MOVING 变成 WAITING，停留 2 秒，
> 然后索引加 1，去下一个点。这张图上的黄点也跟着往后移。
>
> 这里的状态机是**事件驱动**的，100 毫秒 tick 一次。
> 我没有用阻塞等待的原因很实际——在 ROS 2 C++ 里，
> 如果在一个回调里 `.get()` 等 Action 结果，单线程执行器会直接死锁，而且不报错。"

**要点**：这是演示的**核心 30 秒**，必须把状态机的设计讲出来。

---

### 镜头 7｜暂停 / 继续（2:25–2:40）

**操作**：

```bash
ros2 service call /patrol/set_mode patrol_interfaces/srv/SetPatrolMode "{mode: 1}"   # PAUSE
# 等 2 秒，机器人停下
ros2 service call /patrol/set_mode patrol_interfaces/srv/SetPatrolMode "{mode: 2}"   # RESUME
# 机器人继续前往同一航点
```

**讲解词**：

> "暂停会取消当前导航目标，但**保留航点索引**；继续的时候从同一个点重新发起导航。
> 这里我做了一个取舍：Resume 不去"接着计时"，而是重新下发目标——
> 因为机器人可能已经被挪动过，重新导航更安全，而且 Nav2 对"已经在目标点"的目标会立即返回成功，代价可以忽略。"

**要点**：展示"有意为之的设计取舍"，而不是"恰好这样"。

---

### 镜头 8｜安全守护（2:40–3:00）

**操作**：

1. Gazebo 中 `Insert` → Box，放在机器人正前方约 0.2 m。
2. 指出终端 B 或新终端中 `/safety/emergency_stop` 变为 `true`，机器人停下，状态变 `MODE_SAFETY_HOLD`。
3. 右键删除障碍物，机器人自动恢复巡逻。

**讲解词**：

> "最后是安全守护。这是一个独立的节点，订阅激光雷达，
> 在前方 60 度扇区里算最小距离。当距离小于 0.3 米就置位紧急标志。
>
> 现在机器人停住了，状态变成 SAFETY_HOLD。移开障碍物后，它自动恢复继续巡逻。
>
> 有个设计我要特别说明：**安全节点默认不直接发 `/cmd_vel`**。
> 直接抢/写速度总线会导致和 Nav2 控制器竞争，机器人会抖。
> 所以我把职责分开：**安全节点只做"感知和判断"，任务层做"决策和执行"**。
> 阈值用的是迟滞——0.3 米触发、0.6 米解除，中间那段保持原状态，避免在阈值附近抖动。"

**要点**：收尾用架构思维，比堆功能更打动人。

## 6. 现场提问的应对预备（详见 13 文档）

| 可能被问 | 一句话思路 |
| --- | --- |
| 为什么用 Nav2 不自己写？ | 工程上重复造轮子没有收益，集成成熟栈才是正确做法 |
| 为什么用 C++ 不用 Python？ | 岗位要求 + C++ 侧没有现成的 `BasicNavigator`，自己封装 Action 反而能说明我懂机制 |
| 你的状态机为什么不用阻塞写法？ | 会死锁，具体原因见 13 §3.2 |
| 安全节点为什么不直接发 cmd_vel？ | 控制权竞争，违反单一权威原则 |
| 如果换真车要改什么？ | 只换底层驱动，任务层参数化，不用改 |
| 这个项目你自己做的比例是多少？ | 任务层 100% 自研，导航建图集成开源栈（诚实回答） |

### 8.2 录屏前的桌面清理清单
