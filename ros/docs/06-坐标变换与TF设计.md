# 06 坐标变换与 TF 设计

| 项目名称 | ros2-patrol-robot-sim |
| --- | --- |
| 文档编号 | 06 |
| 版本 | v0.1 |

TF（Transform）是 ROS 2 中**最容易出错、最难排查**的部分。
本文档固化本项目的坐标系约定、TF 树结构、时间戳规范与排错流程。

---

## 1. 为什么 TF 值得单独一份文档

在移动机器人系统中，几乎所有跨模块问题最后都会表现为 TF 问题：

| 现象 | 常见根因 |
| --- | --- |
| 机器人在 RViz 里"瞬移" | `map → odom` 由两个节点同时发布 |
| 路径规划总是失败 | 机器人位姿不在代价地图范围内（TF 断裂） |
| `Lookup would require extrapolation into the future` | 时间戳超前于 TF 缓存 |
| `TF_OLD_DATA ignoring data from the past` | 时间戳回退，通常是 `use_sim_time` 不一致 |
| 雷达点云在 RViz 中偏移 | `base_link → base_scan` 静态变换错误 |
| Nav2 一直在恢复行为 | `map → odom` 定位漂移严重 |

**结论**：TF 是系统集成的"神经系统"，必须在设计阶段就把坐标系与权威归属定义清楚。

## 2. 坐标系定义

| 坐标系 | 类型 | 含义 | 发布者（权威） |
| --- | --- | --- | --- |
| `map` | 全局固定 | 地图坐标系，原点在地图建图起点 | —（作为参考根） |
| `odom` | 局部固定 | 里程计坐标系，原点在机器人上电位置 | — |
| `base_footprint` | 机器人本体 | 机器人在地面上的投影（z=0） | — |
| `base_link` | 机器人本体 | 机器人底盘几何中心（TurtleBot3 中约 z=0.01） | — |
| `base_scan` | 传感器 | 激光雷达安装位置 | `robot_state_publisher`（静态） |
| `imu_link` | 传感器 | IMU 安装位置 | `robot_state_publisher`（静态） |
| `wheel_left_link` / `wheel_right_link` | 执行器 | 左右轮 | `robot_state_publisher`（动态，来自 `/joint_states`） |

**本项目自研节点只使用 `map` 一个坐标系**，所有航点均定义在 `map` 下。
这是刻意的简化：任务层不需要关心机器人的具体位姿，只需要下发达标点。

## 3. TF 树结构

```
                              map
                               │
                               │  ← 由 AMCL 发布（动态，周期约 10–50 Hz）
                               │    定位校正：把里程计漂移补偿到 map 系下
                               ▼
                              odom
                               │
                               │  ← 由 Gazebo 差速驱动插件发布（动态）
                               │    纯里程计积分：轮速 × 时间
                               ▼
                        base_footprint
                               │
                               │  ← 由 robot_state_publisher 发布（静态，来自 URDF）
                               ▼
                           base_link
                     ┌─────────┼─────────┬──────────────┐
                     ▼         ▼         ▼              ▼
              wheel_left  wheel_right  base_scan     imu_link
                _link       _link    （LiDAR）        （IMU）
                （动态，来自 /joint_states）
```

### 3.1 各级变换的物理含义

| 变换 | 语义 | 更新来源 | 是否允许丢失 |
| --- | --- | --- | --- |
| `map → odom` | "机器人以为自己在哪里" vs "它实际在哪里" 的校正量 | AMCL 粒子滤波 | ✗ 丢失则 Nav2 无法工作 |
| `odom → base_footprint` | 机器人相对上电点的运动 | 里程计积分 | ✗ 丢失则 TF 树断裂 |
| `base_footprint → base_link` | 固定高度偏移（TB3 约 0.010 m） | URDF | ✗ |
| `base_link → base_scan` | 雷达安装位姿（TB3 在中心，z≈0.17 m） | URDF | ✗ 丢失则雷达数据无法定位 |

### 3.2 为什么是 `base_footprint` 而不是 `base_link` 作为中间层

TurtleBot3 官方 URDF 使用 `base_footprint` 作为地面投影点：

- 2D 导航（Nav2）在平面上工作，`base_footprint` 的 z=0 让 Z 轴处理最简单；
- 代价地图的机器人轮廓以 `base_footprint` 为中心，避免底盘高度引入误差；
- AMCL 的 `base_frame_id` 必须与导航栈一致，**不一致会导致定位完全错乱**。

## 4. 时间戳规范

### 4.1 仿真时间（use_sim_time）

| 项 | 约定 |
| --- | --- |
| 时间源 | Gazebo 通过 `/clock` 话题发布仿真时间 |
| 节点配置 | **所有**涉及时间运算的节点必须 `use_sim_time: true` |
| 获取时间 | 用 `this->now()`（自动遵循 `use_sim_time`），**禁止**用 `std::chrono::system_clock::now()` |
| 涉及节点 | `patrol_node`、`safety_guard_node`、Nav2 全部节点、`slam_toolbox`、`robot_state_publisher`、RViz2 |

### 4.2 校验命令

```bash
# 1. 确认仿真时钟在跑（若无输出 = use_sim_time 配置错误或 /clock 未发布）
ros2 topic hz /clock

# 2. 确认所有节点都拿到 sim time
ros2 param get /patrol_node use_sim_time          # 期望 True
ros2 param get /safety_guard_node use_sim_time    # 期望 True
ros2 param get /controller_server use_sim_time    # 期望 True

# 3. 确认 TF 各段都存在
ros2 run tf2_tools view_frames                    # 生成 frames.pdf
ros2 run tf2_ros tf2_echo map base_footprint      # 应持续输出变换
```

### 4.3 常见时间戳错误与含义

| 错误信息 | 含义 | 根因 |
| --- | --- | --- |
| `Lookup would require extrapolation into the future` | 查询时刻晚于 TF 缓存中最新的时间戳 | TF 发布者滞后；或 `use_sim_time` 为 false 而订阅者在用仿真时间 |
| `TF_OLD_DATA ignoring data from the past` | 收到时间戳回退的数据 | 时钟源切换（真实时间 → 仿真时间）未重启节点 |
| `Timed out waiting for transform` | 缓存中没有该变换 | TF 树断裂，发布者未启动 |
| `Cannot transform: source frame does not exist` | 坐标系名拼错 | 检查 `global_frame` 参数 |

### 4.4 自研节点的时间使用规范

```cpp
// ✓ 正确：遵循 use_sim_time
goal.pose.header.stamp = node_->now();
msg.header.stamp = now();
const double elapsed = (now() - wait_start_).seconds();

// ✗ 错误：绕过 ROS 时间系统，仿真下必然出问题
auto t = std::chrono::system_clock::now();
```

> **注意**：`rclcpp::Time` 的默认构造函数会使用系统时间。
> 成员初始化时必须指定时钟类型：`rclcpp::Time wait_start_{0, 0, RCL_ROS_TIME};`

## 5. TF 排错流程（SOP）

遇到任何"机器人不动 / 乱动 / 定位错乱"的问题，按以下顺序逐层排查：

```
Step 1  /clock 在跑吗？
        ros2 topic hz /clock
        └─ 否 → 检查 use_sim_time 与 Gazebo 插件

Step 2  TF 树完整吗？
        ros2 run tf2_tools view_frames
        打开 frames.pdf，检查是否有一条完整链路：
        map → odom → base_footprint → base_link → base_scan
        └─ 缺 map → odom → AMCL 未激活（检查 lifecycle_manager 日志）
        └─ 缺 odom → base_footprint → Gazebo 插件未加载 / 机器人未 spawn

Step 3  变换数值合理吗？
        ros2 run tf2_ros tf2_echo map base_footprint
        └─ 数值不变化 → 定位或里程计卡死
        └─ 数值跳变（跳几十米）→ map → odom 被多个发布者污染

Step 4  谁在发布 map → odom？
        ros2 topic info /tf --verbose
        确认发布者列表里只有 amcl 一个
        └─ 若同时有 slam_toolbox → 违反了单一权威原则（见 05 §6.3）

Step 5  时间戳超前还是滞后？
        ros2 run tf2_ros tf2_monitor map base_scan
        └─ 关注 "Latest Transform" 与 "Average Delay"

Step 6  用命令行隔离验证 Nav2
        ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
          "{pose: {header: {frame_id: 'map'}, pose: {position: {x: 1.0, y: 0.5}, orientation: {w: 1.0}}}}" --feedback
        └─ 走不通 → 问题在 Nav2/定位/TF，不在自研代码
        └─ 走得通 → 问题在自研节点，查 /patrol/status 与节点日志
```

## 6. 各阶段 TF 提供者矩阵

| 阶段 | `map→odom` | `odom→base_footprint` | 静态 TF | 说明 |
| --- | --- | --- | --- | --- |
| 仅仿真（`simulation.launch.py`） | 无 | Gazebo 插件 | `robot_state_publisher` | 无全局定位，只能看局部 |
| 建图（`mapping.launch.py`） | `slam_toolbox` | Gazebo 插件 | `robot_state_publisher` | SLAM 提供地图与全局定位 |
| 导航（`navigation.launch.py`） | `amcl` | Gazebo 插件 | `robot_state_publisher` | 基于已有地图定位 |
| 巡逻（`patrol.launch.py`） | `amcl` | Gazebo 插件 | `robot_state_publisher` | 同导航 + 任务层 |

> **禁止**：`patrol_node` 与 `safety_guard_node` **绝不发布任何 TF**。
> 若需要机器人位姿，通过订阅 `/amcl_pose` 或 TF 查询接口获取（只读）。

## 7. 坐标变换中使用的数学约定

### 7.1 航点偏航角（yaw）与四元数的转换

```cpp
#include "tf2/LinearMath/Quaternion.h"
#include "tf2_geometry_msgs/tf2_geometry_msgs.hpp"

tf2::Quaternion q;
q.setRPY(0.0, 0.0, yaw);                  // roll=0, pitch=0, yaw 绕 z 轴
goal.pose.pose.orientation = tf2::toMsg(q);
```

**必须使用 `tf2::toMsg`**，不要手工构造四元数。手工构造的常见错误是漏掉 `w` 分量。

| yaw | 四元数 (x, y, z, w) |
| --- | --- |
| 0 | (0, 0, 0, 1) |
| π/2 | (0, 0, 0.707, 0.707) |
| π | (0, 0, 1, 0) |
| -π/2 | (0, 0, -0.707, 0.707) |

### 7.2 yaw 的取值范围

| 项 | 约定 |
| --- | --- |
| 参数输入 | 任意实数（如 `3.14`、`-6.28`），加载时自动归一化到 `(-π, π]` |
| 归一化函数 | `WaypointLoader::normalizeAngle()`（见 04 §3.5） |
| 归一化公式 | `a = fmod(yaw + π, 2π); if (a < 0) a += 2π; return a - π` |
| 边界处理 | `π` 归一化后仍为 `π`（不转成 `-π`），避免与 `-π` 混淆 |

### 7.3 右手坐标系约定

ROS 使用右手坐标系，TurtleBot3 的朝向定义：

```
        +x（前进）
         ▲
         │
  +y ◄───┼───► -y   （+y 在机器人左侧）
         │
         ▼
       -x（后退）
       
  +z 向上（离开地面）
  yaw 绕 +z 逆时针为正
```

**常见误解**：误以为 +y 在右侧。在 ROS 标准下，**+y 指向机器人左侧**，
因此"左手转弯"对应 yaw 增大。

## 8. TF 相关参数对照表

| 参数位置 | 参数名 | 值 | 说明 |
| --- | --- | --- | --- |
| `patrol_node` | `global_frame` | `map` | 航点参考系 |
| `slam_toolbox` | `map_frame` | `map` | SLAM 输出的地图系 |
| `slam_toolbox` | `odom_frame` | `odom` | SLAM 使用的里程计系 |
| `slam_toolbox` | `base_frame` | `base_footprint` | SLAM 使用的机器人本体系 |
| `amcl` | `global_frame_id` | `map` | AMCL 输出的全局系 |
| `amcl` | `odom_frame_id` | `odom` | AMCL 读取的里程计系 |
| `amcl` | `base_frame_id` | `base_footprint` | AMCL 的机器人本体系 |
| `bt_navigator` | `global_frame` | `map` | 行为树导航器的全局系 |
| `bt_navigator` | `robot_base_frame` | `base_link` | 行为树导航器的机器人系 |
| `local_costmap` | `global_frame` | `odom` | 局部代价地图用 odom（连续，无跳变） |
| `global_costmap` | `global_frame` | `map` | 全局代价地图用 map（需全局定位） |

### 8.1 一个必须知道的细节：`bt_navigator.robot_base_frame` 是 `base_link`

Nav2 默认 `robot_base_frame = base_link`，而 AMCL 的 `base_frame_id = base_footprint`。
两者**不一致是官方默认配置，不是错误**——Nav2 内部会通过 TF 查询 `base_link`，
而 `base_link → base_footprint` 的变换由 URDF 提供，链路是通的。

但如果你把 `bt_navigator.robot_base_frame` 改成不存在的坐标系名，就会出现：
`Timed out waiting for transform from base_xxx to map`。

## 10. 快速修复手册

| 症状 | 修复步骤 |
| --- | --- |
| RViz 中机器人消失/在原点 | ① 检查 RViz 的 Fixed Frame 是否设为 `map`（不是 `odom`）<br>② `ros2 run tf2_tools view_frames` 看树是否断<br>③ 用 `2D Pose Estimate` 重新初始化 AMCL |
| `map→odom` 跳变几十米 | 检查是否同时运行了 `slam_toolbox` 和 `amcl`；只保留一个 |
| `base_footprint` 与 Gazebo 位置不符 | 用 `2D Pose Estimate` 手动校正初始位姿；检查地图是否与当前世界匹配 |
| TF 查询超时 | ① 确认 `/clock` 在跑；② 全部节点 `use_sim_time=true`；③ 提高 `tf_buffer_duration` |
| 雷达点云不显示 | ① 检查 RViz 中 Fixed Frame 与 LaserScan 的 Topic；② 检查 `base_link→base_scan` 是否存在 |
| 仿真时间跳变导致重建 TF 失败 | 重启所有节点（不要单独重启某个节点，时钟基准会不一致） |
