## 1. 计划前提与假设

| 项 | 内容 |
| --- | --- |
| 人员 | 1 人（全栈：环境、开发、测试、文档、演示） |
| 已有条件 | Windows 开发机、虚拟机软件、网络可用、**ROS 2 与 TurtleBot3 环境需自建** |
| 目标岗位 | 机器人 TPM / 系统工程师 / 具身智能集成 |
| 交付物 | 可运行仓库 + 17 份文档（README + docs/00 ~ 16）+ 3 分钟演示录屏 |
| 时间盒 | 每日 8 小时，**不熬夜**（熬夜导致的调试效率下降是最大隐性成本） |

### 1.1 关键排期假设

1. **环境搭建占用 0.5 天**（若全新安装 ROS 2 + TurtleBot3，可能占满全天——见 §6 降级预案）。
2. **不写一行底层算法代码**（SLAM / 规划 / 控制全用现成栈）。
3. **地图采集只需一次**，且采集后不再变更世界。
4. **文档与代码同步产出**，不把文档堆到最后一天。

## 6. 降级预案（时间不够时怎么砍）

> **原则**：先保证"能演示"，再保证"能讲解"，最后才追求"完整"。

### 预案 P1：环境搭建超时（Day1 上午未完成）

| 措施 | 影响 |
| --- | --- |
| 使用鱼香 ROS 一键安装脚本替代手动 deb 安装 | 省 0.5 h，但排障困难 |
| 跳过虚拟机优化（剪贴板/3D 调优） | 演示体验下降，不影响功能 |
| **不**安装 CycloneDDS，用默认 Fast DDS | 通信开销略高，功能不变 |
| 若仍失败 → 降到 Ubuntu 双系统或找现成的 ROS 2 镜像 | 需额外 2 h，需从 Day1 下午挤 |

### 预案 P2：SLAM 建图不理想（Day1 下午）

| 措施 | 影响 |
| --- | --- |
| 使用 TurtleBot3 官方 `map.pgm`（`turtlebot3_navigation2/map/map.yaml`）替代自建地图 | 丧失"自建地图"亮点，但导航可用 |
| 换用 `cartographer` 建图 | 需额外 0.5 h，参数不同 |
| 牺牲建图精度：只要能连通即可 | 定位精度下降，导航成功率下降 |

### 预案 P3：巡逻节点调试超时（Day2 下午）

按以下顺序**逐步降级**，每降一级省 0.5–1 h：

| 降级级别 | 砍掉什么 | 保留什么 | 影响 |
| --- | --- | --- | --- |
| L1 | 砍掉 `RESET` 模式与 `skip_failed_waypoint` | START/PAUSE/RESUME/STOP、重试 | 几乎无损 |
| L2 | 砍掉超时保护（`waypoint_timeout_sec`） | 重试机制 | 失去一个"工程细节"讲述点 |
| L3 | 砍掉 `PAUSED` 状态，PAUSE 直接等价于 STOP | 基本巡逻循环 | 失去模式控制演示 |
| L4 | 砍掉状态机，用简单的"索引 + 标志"顺序执行 | 航点循环 + 可视化 | **风险最大**，会失去"事件驱动状态机"这一核心亮点 |
| L5 | 降级为 Python 实现（放弃 C++） | 功能完整 | **不推荐**，与用户要求冲突 |

> **底线**：绝不降到 L5。宁可少做功能，也保证 C++ 主线。

### 预案 P4：Day3 时间不够

| 措施 | 影响 |
| --- | --- |
| 安全守护降级为"仅发布标志，不做联动恢复"（需手动 RESUME） | 功能残缺但不影响主演示 |
| 跳过性能测试与长稳测试，只留主用例 | 缺少 NFR 证据 |
| 演示录屏用未剪辑的一次性录制 | 质量下降，但仍可交付 |
| 长稳测试改为 10 分钟 | 偏离 NFR-05 的 30 min 要求，需在文档中如实说明 |
