## 1. 架构目标与驱动因素

| 驱动因素 | 来源 | 对架构的要求 |
| --- | --- | --- |
| 3 天交付 | 01 §2.3 | 复用成熟栈，自研部分收敛到 2 个节点 |
| 系统集成能力证明 | 01 §1.2 | 必须跨层联调：仿真层 / 抽象层 / 导航层 / 任务层 |
| 用 C++ 而非 Python | 用户要求 | 自研节点全部 C++；涉及 Action / 参数 / TF 的原生用法 |
| 可演示、可讲解 | 01 §3 | 必须有可视化输出与清晰的模块边界 |
| 可复现 | AC-01 | 所有依赖来自官方源，所有配置参数化 |

**核心架构原则**：

1. **不做重复发明**：定位、建图、规划、控制全部交给成熟开源栈。
2. **自研只做差异层**：任务编排（巡逻）与安全策略（守护）——这两层没有现成通用实现。
3. **单向依赖**：任务层依赖导航层，导航层依赖抽象层，绝不反向。
4. **接口先行**：先定义 msg/srv/topic，再写实现。
5. **可独立测试**：纯逻辑类（航点解析、状态机）不依赖 ROS 运行时。

## 2. 总体架构

### 2.1 分层视图

```
┌───────────────────────────────────────────────────────────────────────┐
│ L5 交互层                                                              │
│   RViz2（地图/雷达/TF/路径/Marker）  │  键盘遥控  │  ros2 CLI  │  自定义 │
│                                       │            │  (topic/  │  Service│
│                                       │            │   action) │  调用   │
└───────────────────────────┬───────────────────────────────────────────┘
                            │ 观察 / 指令
┌───────────────────────────▼───────────────────────────────────────────┐
│ L4 任务层（★ 自研，C++17）                                             │
│   ┌──────────────────────────┐     ┌───────────────────────────────┐  │
│   │ patrol_node              │◄────┤ safety_guard_node             │  │
│   │  · 巡逻状态机            │紧急 │  · 前向扇区最小距离            │  │
│   │  · 航点调度/重试/超时    │标志 │  · 迟滞逻辑                    │  │
│   │  · MarkerArray 可视化    │     │  · /safety/* 话题              │  │
│   │  · SetPatrolMode 服务    │     └───────────────────────────────┘  │
│   └──────────┬───────────────┘                                        │
└──────────────┼────────────────────────────────────────────────────────┘
               │ NavigateToPose Action（目标位姿 / 反馈 / 结果）
┌──────────────▼────────────────────────────────────────────────────────┐
│ L3 导航与建图层（开源栈）                                              │
│   ┌──────────────────────────────────────────────────────────────┐    │
│   │ Nav2                                                          │    │
│   │  bt_navigator │ planner_server │ controller_server            │    │
│   │  behavior_server │ waypoint_follower │ lifecycle_manager      │    │
│   │  amcl（定位）                                                 │    │
│   └──────────────────────────────────────────────────────────────┘    │
│   ┌──────────────────────────────────────────────────────────────┐    │
│   │ slam_toolbox（离线建图，仅建图阶段运行）                       │    │
│   └──────────────────────────────────────────────────────────────┘    │
└──────────────┬────────────────────────────────────────────────────────┘
               │ /map  /scan  /odom  /tf  /cmd_vel
┌──────────────▼────────────────────────────────────────────────────────┐
│ L2 抽象层（ROS 2 通信中间件 DDS）                                      │
│   话题（Topic）│ 服务（Service）│ 动作（Action）│ 参数（Parameter）│ TF │
└──────────────┬────────────────────────────────────────────────────────┘
               │ gazebo_ros 插件桥接
┌──────────────▼────────────────────────────────────────────────────────┐
│ L1 仿真层                                                              │
│   Gazebo Classic 11 + turtlebot3_gazebo（世界 + 模型 + 传感器插件）      │
│   TurtleBot3 Burger：轮式差速底盘 + 360° LiDAR + IMU + 里程计            │
└───────────────────────────────────────────────────────────────────────┘
```

### 2.2 分层职责说明

| 层 | 职责 | 变化频率 | 归属 |
| --- | --- | --- | --- |
| L1 仿真层 | 提供物理世界与传感器数据 | 低 | 第三方 |
| L2 抽象层 | 提供与硬件无关的通信原语 | 极低 | ROS 2 |
| L3 导航/建图层 | 建图、定位、规划、控制 | 低 | 第三方（配置为主） |
| L4 任务层 | 任务编排与安全策略 | **高** | **自研** |
| L5 交互层 | 人机接口与可视化 | 中 | 复用 + 少量自研 |

> **设计意图**：把自研部分集中在变化频率最高的 L4，同时让它只依赖 L3 的稳定接口（Action），
> 这样即使将来换成真车或其他仿真器，L4 的代码几乎不用改——这是本项目最值得讲的架构点。

## 3. 技术选型决策记录（ADR）

### ADR-01 为什么基于 Nav2 而不是自研导航

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 背景 | 需要机器人自主从 A 点移动到 B 点，涉及全局规划、局部控制、避障、恢复行为 |
| 选项 A | 自研：A* 全局规划 + DWA 局部控制 + 自建代价地图 |
| 选项 B | 使用 Nav2（bt_navigator + planner_server + controller_server + amcl） |
| 决策 | **选 B** |
| 理由 | 自研需要处理代价地图膨胀、运动学约束、恢复行为、参数整定，工作量 ≥ 2 周且几乎必然比 Nav2 差。工程上正确做法是集成成熟栈。"能跑通并讲清 Nav2 的模块与数据流"比"自己写了个能撞墙的 A*"更有价值 |
| 代价 | 需要理解 Nav2 的生命周期节点、行为树、参数体系，学习成本前置 |
| 缓解 | 用 04/05 文档把 Nav2 的接口与参数固化下来，只暴露必要的部分 |

### ADR-02 为什么自研节点用 C++ 而非 Python

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 背景 | 原方案（DeepSeek 建议）使用 Python + `nav2_simple_commander.BasicNavigator` |
| 选项 A | Python：开发快，`BasicNavigator` 封装好 |
| 选项 B | C++17：需自己封装 Action Client，但更贴近生产工程 |
| 决策 | **选 B** |
| 理由 | ① 用户明确要求 C++ 为主语言；② 岗位要求里 C++ 是硬通货，Python 脚本容易被认为"只会调包"；③ C++ 侧没有 `BasicNavigator` 的现成封装（Humble 下 `nav2_simple_commander` 以 Python 为主），自己封装 Action Client 反而是**可讲述的技术贡献点**；④ 强制处理回调、线程、QoS 等真实工程问题 |
| 代价 | 开发速度慢于 Python；需处理执行器与线程安全 |
| 缓解 | 把封装集中在 `NavClient` 一个类里，其余逻辑保持简单；用 04 文档给出完整代码直接复制 |

### ADR-03 为什么选 TurtleBot3 Burger

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 背景 | 需要一个仿真机器人平台 |
| 选项 | TurtleBot3 Burger / Waffle / 自定义差速小车 / 机械臂 |
| 决策 | **TurtleBot3 Burger** |
| 理由 | ① 官方提供 Gazebo 世界、模型、launch、Nav2 参数，零配置成本；② 社区教程最多，遇错易搜到答案；③ Burger 便宜模型、体积小、单线雷达，仿真开销低；④ `waffle` 有深度相机，但本期不用视觉，Burger 更轻 |
| 代价 | 平台具体性导致与岗位实际机型不完全一致 |
| 缓解 | 在 04 文档中抽象话题名/坐标系名/雷达参数，为真车迁移留出口（见 §9） |

### ADR-04 为什么用原生 Action Client 而不是 `nav2_simple_commander` C++ 版

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 背景 | 需要向 Nav2 下发导航目标并获取反馈与结果 |
| 选项 A | 依赖 `nav2_simple_commander` 的 C++ `BasicNavigator`（Humble 下成熟度与文档不足，不同发行版 API 有差异） |
| 选项 B | 直接用 `rclcpp_action::Client<nav2_msgs::action::NavigateToPose>` |
| 决策 | **选 B**，并封装为自研 `NavClient` 类 |
| 理由 | ① 只依赖 `nav2_msgs`，依赖面最小、最稳定；② 自己封装可以按巡逻业务需要裁剪接口（发送/取消/超时/重试）；③ 面试时可讲清 Action 的 goal / feedback / result 三段式机制，比"我调了个库"有含量 |
| 代价 | 需自己处理 `goal_response_callback` / `feedback_callback` / `result_callback` 与状态维护 |
| 缓解 | 04 §4 给出完整实现与回调时序图 |

### ADR-05 为什么巡逻节点用事件驱动状态机而非阻塞式调用

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 背景 | 巡逻逻辑需要"发目标 → 等到达 → 停 2 秒 → 发下一个"，最直观的写法是在回调里阻塞等待结果 |
| 选项 A | 阻塞式：`client->async_send_goal(...).get()` 然后轮询 `isTaskComplete()` |
| 选项 B | 事件驱动：100 ms 定时器 tick 驱动状态机，结果由 `result_callback` 写入标志 |
| 决策 | **选 B** |
| 理由 | ① 选项 A 在单线程执行器（`SingleThreadedExecutor`）下会**死锁**——回调需要执行器线程才能触发，而执行器线程正被你阻塞；这是 ROS 2 C++ 最经典的坑。② 选项 B 天然支持 PAUSE / 紧急暂停等外部事件插入；③ 状态机可脱离 ROS 单独单元测试（满足 NFR-11） |
| 代价 | 状态多了以后可读性下降，需要状态迁移表 |
| 缓解 | 04 §5.1 给出显式状态枚举 + 迁移表 + tick 伪代码；非阻塞设计同时在 README 中作为技术亮点说明 |

### ADR-06 为什么安全守护节点不直接发布 `/cmd_vel`

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 背景 | 障碍过近时最直接的做法是安全节点直接发零速到 `/cmd_vel` |
| 选项 A | 安全节点直接抢占总线发 `/cmd_vel` |
| 选项 B | 安全节点只发布状态标志，由任务层 cancel 导航目标 |
| 决策 | **选 B 为默认**，A 作为可选降级（参数 `allow_cmd_vel_override` 默认 `false`） |
| 理由 | ① 两个发布者同时写 `/cmd_vel` 会导致控制权竞争与机器人抖动，属于架构缺陷；② Nav2 本身有恢复行为，外部盲目接管会破坏其行为树状态；③ 分层清晰：**安全节点负责"感知与判断"，任务层负责"决策与执行"** |
| 代价 | 响应链更长（scan → safety → patrol → cancel → Nav2 停止），延迟增加约一个 tick 周期 |
| 缓解 | tick 设为 100 ms，最坏响应约 200 ms；激光数据本身还有更低层的 `stop_distance` 兜底（Gazebo 中不会真撞） |

### ADR-07 为什么建图用 `slam_toolbox` 而非 `cartographer`

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳（备选保留） |
| 背景 | 需要一次性生成栅格地图 |
| 选项 | `slam_toolbox` / `cartographer`（TurtleBot3 官方示例） |
| 决策 | **主用 `slam_toolbox`**，`cartographer` 作为备选 |
| 理由 | ① `slam_toolbox` 是纯 ROS 2 原生实现，参数语义清晰，与 Nav2 生态一致（同作者维护）；② 支持在线异步模式，建图时 RViz 响应更流畅；③ 官方 apt 包 `ros-humble-slam-toolbox` 安装即可用，无需编译 |
| 代价 | 参数整定需微调（`minimum_travel_distance` 等） |
| 缓解 | 08 文档提供默认参数与调参建议 |

### ADR-08 为什么用两个自研节点而不是一个大节点

| 项 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 背景 | 巡逻与安全守护可以写在一个节点里 |
| 决策 | **拆成 2 个节点** |
| 理由 | ① 单一职责：安全守护即使在巡逻停止时也应持续监控；② 独立进程崩溃隔离；③ 便于单独演示（可只跑安全守护展示波形）；④ 体现"节点粒度设计"的架构能力，面试可讲 |
| 代价 | 多一层话题通信 |
| 缓解 | 标志用 `transient_local` QoS，避免订阅者晚启动丢失状态 |

## 4. 包与模块划分

### 4.1 包结构

```
ros2-patrol-robot-sim/
├── scripts/
│   ├── install_deps.sh
│   ├── build.sh
│   └── record_demo.sh
└── src/
    ├── patrol_interfaces/            # 接口定义包（ament_cmake）
    ├── patrol_robot_core/            # 核心实现包（ament_cmake，C++17）
    └── patrol_robot_bringup/         # 启动与配置包（ament_cmake）
```

### 4.2 包职责

| 包 | 类型 | 职责 | 对外产出 |
| --- | --- | --- | --- |
| `patrol_interfaces` | 消息包 | 定义自研 msg / srv | `PatrolStatus.msg`、`SetPatrolMode.srv` |
| `patrol_robot_core` | C++ 实现包 | 巡逻状态机、导航客户端封装、航点加载、安全守护 | 2 个可执行文件：`patrol_node`、`safety_guard_node` |
| `patrol_robot_bringup` | 配置包 | launch 文件、YAML 参数、RViz 配置、地图文件、世界文件 | 4 个 launch + 全部配置资产 |

### 4.3 模块（编译单元）划分

`patrol_robot_core` 内部按"纯逻辑 / ROS 胶水"分离：

| 模块 | 文件 | 依赖 ROS | 职责 |
| --- | --- | --- | --- |
| 航点加载器 | `waypoint_loader.{hpp,cpp}` | 仅 `rclcpp::Node` 参数接口 | 参数解析、校验、位姿构造 |
| 导航客户端 | `nav_client.{hpp,cpp}` | `rclcpp_action`、`tf2` | 封装 NavigateToPose Action |
| 巡逻状态机 | `patrol_state_machine.{hpp,cpp}` | **不依赖** | 状态迁移与决策（纯逻辑） |
| 巡逻主节点 | `patrol_node.cpp` | `rclcpp` | 定时器 tick、话题/服务、Marker |
| 安全守护节点 | `safety_guard_node.cpp` | `rclcpp` | 激光扇区计算、迟滞、状态发布 |
| 安全算法 | `safety_evaluator.{hpp,cpp}` | **不依赖** | 扇区距离与迟滞判定（纯逻辑） |

> 依赖倒置：状态机与安全算法不包含任何 ROS 头文件，因此可用 gtest 做纯逻辑测试（NFR-11）。

### 4.4 依赖关系图

```
                 patrol_interfaces
                    ▲          ▲
                    │          │ (msg/srv)
        patrol_robot_core ─────┤
                    ▲          │
                    │          ▼
        patrol_robot_bringup ───┘  (launch 引用 core 的可执行文件)

外部依赖：
  patrol_interfaces      → rosidl_default_generators, std_msgs, geometry_msgs
  patrol_robot_core      → rclcpp, rclcpp_action, nav2_msgs, geometry_msgs,
                            sensor_msgs, nav_msgs, visualization_msgs, tf2,
                            tf2_geometry_msgs, patrol_interfaces
  patrol_robot_bringup   → launch, launch_ros, nav2_bringup, slam_toolbox,
                            turtlebot3_gazebo, turtlebot3_navigation2
```

**禁止依赖**：`patrol_interfaces` 不得依赖 `patrol_robot_core`；`patrol_robot_core` 不得依赖 `patrol_robot_bringup`。

## 5. 运行时视图

### 5.1 节点拓扑（巡逻阶段）

```

              /scan ───►│ 扇区最小距离 + 迟滞判定      │

                                   │ /safety/emergency_stop
                                   ▼
   ┌──────────────────────────┐         ┌──────────────────────────┐

   │  · tick 100ms            │────────►│ /navigate_to_pose        │
   │  · 状态机                │◄────────│ feedback / result        │
   │  · MarkerArray / status  │         │ bt_navigator → planner → │
   └──────────┬───────────────┘         │ controller → /cmd_vel    │
              │                         └──────────┬───────────────┘
              │ /patrol/status, /patrol/markers    │
              ▼                                    ▼

```

### 5.2 启动阶段划分

| 阶段 | 启动内容 | 说明 |
| --- | --- | --- |
| 阶段 1 | Gazebo + 世界 + 机器人 spawn | 提供 `/scan`、`/odom`、`/tf` |
| 阶段 2 | `robot_state_publisher` | 从 URDF 发布静态 TF |
| 阶段 3 | Nav2（生命周期管理器 → map_server → amcl → planner → controller → bt_navigator） | 由 `lifecycle_manager` 按依赖顺序 configure/activate |
| 阶段 4 | `patrol_node` + `safety_guard_node` | 等待 Action Server 就绪后再接受命令 |

> **关键顺序约束**：`patrol_node` 必须在 Nav2 Action Server 激活之后再发目标，
> 否则目标会被静默丢弃。实现上通过 `wait_for_action_server()` 显式等待（见 04 §4.3）。

```
  │                  │                │◄── NavigateToPose goal ──────│
  │                  │                │── feedback ──►│              │
  │                  │                │── result ────►│              │
```

### 6.2 导航与巡逻阶段

```
已保存地图 ──► map_server ──► /map
                                 │
/scan ──────────────────────► amcl ──► map→odom ──► TF
                                 │
patrol_node ──► NavigateToPose goal ──► bt_navigator
                                          │
                    ┌─────────────────────┴──────────────────┐
                    ▼                                        ▼
              planner_server                          controller_server
              (全局路径 /plan)                        (局部控制 /cmd_vel)
                                                              │
                                                              ▼
                                                      Gazebo 差速底盘
```

### 6.3 数据流向约束

| 约束 | 说明 |
| --- | --- |
| 单一控制源 | 只允许 Nav2 的 `controller_server` 发布 `/cmd_vel`（除非显式开启安全接管） |
| 单一时间源 | 仿真下所有节点必须 `use_sim_time = true`，由 Gazebo 提供 `/clock` |
| 单一 TF 权威 | `map→odom` 由 AMCL 发布；`odom→base_footprint` 由仿真插件发布；静态部分由 `robot_state_publisher` 发布。**任何自研节点都不得发布 TF** |
| 单一地图源 | 巡逻阶段只有 `map_server` 提供 `/map`，SLAM 不得同时运行 |

**部署说明**：

- 所有节点在同一台机器上运行，通过 DDS 本地回环通信，`ROS_DOMAIN_ID` 用于隔离不同实验。

- 推荐 `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`，TurtleBot3 官方推荐，仿真中通信开销更低。

## 8. 关键场景时序

### 8.1 场景：自动巡逻一轮（3 航点）

```
时间轴(mock)  patrol_node                 Nav2                    结果
   t0         IDLE
   t1         START ──► 状态=PATROLLING, idx=0
   t2         sendGoal(WP0)  ──────────►
   t3                                 planner 规划 → controller 执行
   t4         ◄── feedback(distance_remaining)       状态话题更新
   t5         ◄── result(SUCCEEDED)                  到达 WP0
   t6         等待 wait_sec=2.0s                     状态=WAITING
   t7         idx=1, sendGoal(WP1) ──────►
   ...
   t_n        idx=2 完成 → 循环 1 结束
   t_n+1      loop 未达上限 → idx=0 重新开始
   t_end      loop 达上限 → 状态=IDLE, 日志"patrol finished"
```

### 8.2 场景：安全守护触发暂停

```
 safety_guard        patrol_node              Nav2
     │                    │                    │
     │ /scan 前方 0.25m (< stop=0.3m)
     │ emergency_stop=true │                    │
     │───────────────────►│                    │
     │                    │ cancel 当前目标 ───►│
     │                    │ 状态=PATROLLING(SAFETY_HOLD)
     │                    │                    │
     │ /scan 前方 0.8m (> resume=0.6m)
     │ emergency_stop=false│                    │
     │───────────────────►│                    │
     │                    │ 重新 sendGoal(当前 idx)►│
     │                    │ 状态=PATROLLING     │
```

### 8.3 场景：航点导航失败与重试

```
patrol_node                                   Nav2
    │ sendGoal(WP1) ──────────────────────────►
    │ ◄── result(ABORTED)   [被障碍困住]
    │ retry_count=1 < max_retries=3
    │ sendGoal(WP1) ──────────────────────────►
    │ ◄── result(ABORTED)   retry_count=2
    │ sendGoal(WP1) ──────────────────────────►
    │ ◄── result(ABORTED)   retry_count=3 → 达到上限
    │ if skip_failed_waypoint: idx=2 继续
    │ else: 状态=FAILED，发布错误码，等待人工介入
```

## 10. 架构风险与权衡

| 风险 | 影响 | 权衡决策 |
| --- | --- | --- |
| 自研任务层与 Nav2 职责边界模糊 | 可能出现双重控制 | ADR-06：明确分层，安全节点不碰 `/cmd_vel` |
| 事件驱动状态机状态膨胀 | 可读性下降 | 状态数量控制在 6 个以内 + 迁移表 |
| 依赖 Nav2 内部行为树 | Nav2 升级可能破坏兼容 | 锁定 Humble 版本；不自定义 BT XML |
| 虚拟机 3D 加速不稳 | 演示失败 | 预案：headless + 提前录制（见 11 文档） |
| 自封装 Action Client 有 bug 风险 | 导航无法触发 | 通过 TC-U-01/02 单元测试 + 先用 `ros2 action send_goal` 验证 Nav2 侧正常 |
